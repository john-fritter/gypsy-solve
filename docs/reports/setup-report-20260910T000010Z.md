The path is my preference for the project layout because code, runner metadata, and resumable output stay together. The free-space number is not a recommendation to begin a large batch: 96% utilization on RAID0 leaves too little operational margin. Before a real run, measure the result record size, reserve space for partial/retry metadata, and either clear/provision storage or move the batch output to a safer volume. The runner should keep this path configurable.

## What surprised me / what I would do differently

1. **The box is materially tighter than the nominal disk size suggests.** It has 7.3 TiB total but only 284.8 GiB available, and it is a RAID0 root filesystem. I would make storage provisioning and backup posture an explicit prerequisite before any thousands-of-deals run.
2. **Memory pressure is already present.** Only about 4.9 GiB is available and swap is almost full. I would not size a fixed transposition table from the nominal 15 GiB; I would reserve substantial memory for existing services and benchmark one solve first.
3. **The host is shared with an active production stack.** Four workers is a starting ceiling, not a promise. A runner needs bounded concurrency, per-deal incremental writes, restart/resume behavior, and a way to stop cleanly without filling the filesystem.
4. **The repository is intentionally at setup stage.** There is no solver, batch runner, analysis package, WASM, or Klondike validation yet. Producing a percentage now would be fabricated; the first real scientific gate is implementing the solver and validating the pipeline against Klondike.
5. **The requested default-branch change needs an authenticated GitHub settings path.** I would either authenticate `gh` on the host or have John change the setting from GitHub. PR #1 should remain open until John decides.
